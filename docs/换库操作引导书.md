# BeModel 换库操作引导书

> 目标读者：要把一个**新的 MySQL 业务库**接入 BeModel 平台、并让它支持智能问数 / 指标巡检 / 质控溯源的实施或运维人员。
>
> 平台定位：数据**不搬家、不复制**。平台只登记连接、扫描表结构、维护「概念属性 ↔ 物理列」映射，所有数字始终从业务库实时查出。

---

## 0. 适用范围与硬性前提

| 项         | 要求                                    | 原因                                                                                             |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 数据库类型 | **MySQL**（或协议兼容库）         | 后端写死`com.mysql.cj.jdbc.Driver` 与 `jdbc:mysql://` 连接串（`DatasourceService.jdbc()`） |
| 连接账号   | 建议**只读账号**                  | 平台侧虽有 SQL 白名单（只放 SELECT），账号只读是第二道保险                                       |
| 网络连通   | 平台服务器 → 业务库 host:port 可达     | 注册页的「测试连接」会先跑`SELECT 1`                                                           |
| 账号权限   | 对目标库有`information_schema` 读取权 | 表结构扫描依赖它                                                                                 |
| 操作角色   | 平台 ADMIN 或 EDITOR                    | VIEWER 无写权限                                                                                  |

**换库后能干什么**：智能问数（Ontology2SQL）、口径卡、指标巡检、质控、链路追溯——这些是通用执行框架，由「数据源 + 映射 + 本体」三样元数据驱动。

**换库后不能干什么**：

- 跨库 JOIN：SQL 只允许 JOIN **同一数据源内**的表，跨库核对是分别查询后在应用层比对；
- 未映射的表/列对 AI 不可见：白名单只包含 `confirmed=1` 的映射，没绑定 = 问不到（这是安全设计）。

## 1. 全景流程（六步）

```
① 注册数据源 ──> ② 测试连接 ──> ③ 扫描表结构 ──> ④ 建映射（AI 推荐 + 人工确认）
                                                        │
⑥ 验证问数  <────────────── ⑤ 发布本体版本  <───────────┤
                         （概念不够先补建，见 §5）
```

对应页面：`/datasource`（①②③④）、`/ontology`（⑤ 补概念）、架构全貌页可看**映射覆盖度**。

## 3. 逐步操作

### 步骤 ①：注册数据源

**页面操作**：登录平台（EDITOR 及以上）→ 左侧导航「数据源绑定」→ 新建数据源，填：

| 字段          | 示例值                      |
| ------------- | --------------------------- |
| 数据源编码    | `DS_PEIS`                 |
| 名称          | 体检系统库                  |
| host / port   | `192.168.1.50` / `3306` |
| 库名          | `demo_peis`               |
| 用户名 / 密码 | `peis_ro` / `******`    |

密码落库前自动 AES-GCM 加密（`ENC:` 前缀密文），列表页永远只显示 `****`。

**等价 API**：

```bash
curl -X POST http://127.0.0.1:18080/api/datasource \
  -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" \
  -d '{
    "dsCode": "DS_PEIS", "dsName": "体检系统库", "productName": "PEIS",
    "host": "192.168.1.50", "port": 3306, "dbName": "demo_peis",
    "username": "peis_ro", "password": "******"
  }'
```

### 步骤 ②：测试连接

页面点「测试」，后端执行 `SELECT 1`（5 秒超时）。失败先查网络 / 防火墙 / 账号。

```bash
curl -X POST http://127.0.0.1:18080/api/datasource/test -d '{...同上...}'
# 返回 {"code":0,"data":true} 即通
```

### 步骤 ③：扫描表结构

页面点「扫描」，后端只读 `information_schema`，把表/列快照落平台库（`bm_physical_table` / `bm_physical_column`）。**重复扫描是先删后建，幂等。**

```bash
curl -X POST http://127.0.0.1:18080/api/datasource/scan/DS_PEIS
# 返回 {"tableCount": 2}
```

扫完后「物理表」下拉能看到 `peis_exam`、`peis_item_result`，以及每列的类型、注释、是否主键。

### 步骤 ④：建映射（核心环节，最花时间）

#### 4.0 先搞懂：映射到底是在填一张什么表

映射其实就是一张**翻译对照表**，一行 = 一条「这个物理列是哪个概念的哪个属性」：

```
数据源      表名             物理列          →  概念            属性
DS_PEIS   peis_exam        exam_no        →  PEIS_EXAM      exam_no
DS_PEIS   peis_exam        exam_status    →  PEIS_EXAM      status
DS_PEIS   peis_item_result abnormal       →  PEIS_ITEM_RESULT  abnormal
```

**为什么必须填这张表？看有/没有映射的差别：**

用户问：「张三的体检做完了吗？」

- **没有映射时**：AI 不知道 `peis_exam` 这张表存在（表不在白名单），也猜不到「做完」对应哪个字段 → 答不了，这句话落入概念缺口。
- **有映射时**：AI 看到的语义上下文里明确写着「`peis_exam` 表有 `person_name`（姓名）、`exam_status`（状态，值字典 0=在检/1=完成/2=作废）」→ 生成：

```sql
SELECT exam_no, person_name, exam_date, exam_status
FROM peis_exam
WHERE person_name LIKE '%张三%'
LIMIT 100
```

  用户看到的回答里「已完成」，而库里存的其实是 `exam_status='1'`——这层翻译就是值字典干的。

#### 4.1 映射前先确认本体里有对应概念

映射的箭头右边必须是已存在的概念属性。体检场景平台原本体没有「体检」概念，需先补建（见 §5），假设已发布：

| 概念 code            | 名称         | 关键属性                                              |
| -------------------- | ------------ | ----------------------------------------------------- |
| `PEIS_EXAM`        | 体检记录     | exam_no(主键)、person_name、gender、exam_date、status |
| `PEIS_ITEM_RESULT` | 体检项目结果 | result_id(主键)、item_name、result_value、abnormal    |

> 概念属性是「标准词」，物理列是「方言」。建映射 = 让方言对上标准词。概念没建好，映射就没有目标可指。

#### 4.2 点「AI 推荐」，看懂它返回什么

对 `peis_exam` 点 AI 推荐（`GET /api/mapping/ai-suggest?dsCode=DS_PEIS&tableName=peis_exam`）。后端把**表的全部列（含注释）**和**全部已发布概念的属性清单**一起喂给大模型，让它逐列配对。真实返回长这样：

```json
{
  "llmUsed": true,
  "model": "deepseek-v4-flash",
  "suggestions": [
    {"column":"exam_no",     "conceptCode":"PEIS_EXAM", "attrCode":"exam_no",   "confidence":0.98, "reason":"主键，名称与属性完全一致"},
    {"column":"person_name", "conceptCode":"PEIS_EXAM", "attrCode":"person_name","confidence":0.95,"reason":"注释'姓名'与属性'姓名'一致"},
    {"column":"gender",      "conceptCode":"PEIS_EXAM", "attrCode":"gender",   "confidence":0.90, "reason":"注释'性别'与属性'性别'一致"},
    {"column":"exam_status", "conceptCode":"PEIS_EXAM", "attrCode":"status",   "confidence":0.72, "reason":"列名含status，注释'状态'，疑为体检状态"},
    {"column":"exam_date",   "conceptCode":"PEIS_EXAM", "attrCode":"exam_date","confidence":0.88, "reason":"注释'体检日期'与属性一致"},
    {"column":"remark",      "conceptCode":"",           "attrCode":"",         "confidence":0.0,  "reason":"本体中无备注类属性，未匹配"}
  ]
}
```

**怎么用这份建议（人工把关的三条经验）：**

- `confidence ≥ 0.9` 且理由是「名称/注释一致」→ 大胆确认；
- `confidence 0.6~0.85` → 重点核对，AI 最容易在「同名列、语义不同」上翻车（比如把「操作员状态」配到「医嘱状态」）；
- `attrCode` 为空 → 说明本体缺这个属性，先别硬配（见 4.5 场景五）。

**没配 DeepSeek API Key 也能用**：自动降级为规则匹配（列名包含属性编码、或注释包含属性名，统一给 0.6 置信度），此时人工核对工作量更大一些。

#### 4.3 五种典型场景，逐个举例

**场景一：名字对得上——直接绑，最简单**

```
peis_exam.person_name（注释：姓名） → PEIS_EXAM.person_name（属性名：姓名）
```

一眼对一眼，确认即可。这类通常占六七成。

**场景二：枚举列——必须配值字典，否则 AI 翻译不出中文**

`exam_status` 列存的是 `0/1/2` 这种码。映射时在 valueMap 里写清对照：

```json
{"dsCode":"DS_PEIS","tableName":"peis_exam","columnName":"exam_status",
 "conceptCode":"PEIS_EXAM","attrCode":"status",
 "valueMap":"{\"0\":\"在检\",\"1\":\"完成\",\"2\":\"作废\"}",
 "confirmed":1,"source":"MANUAL"}
```

效果：用户问「作废的体检单有多少」→ AI 自动把「作废」反解成 `exam_status='2'`。
**不配的后果**：AI 只知道这列存 `0/1/2`，不知道哪个是「作废」，要么答不了、要么瞎猜一个码。

> 值字典去哪查？三个途径：① 找新库的字典表；② 直接抽样看数据 `SELECT exam_status, COUNT(*) FROM peis_exam GROUP BY exam_status`；③ 问业务方。**宁可空着让 AI 答不了，也不要配错**——配错了 AI 会一本正经地查错数。

**场景三：同一个业务字段出现在多张表——每张表都要各绑一次**

体检库里 `peis_exam` 和 `peis_item_result` 都有 `exam_no`。映射不是按列名全局生效，而是**按「表+列」逐行绑定**：

```
peis_exam.exam_no         → PEIS_EXAM.exam_no        （确认）
peis_item_result.exam_no  → PEIS_EXAM.exam_no        （也要确认！）
```

漏绑第二张表的后果：问「某次体检的异常项目」时，`peis_item_result` 里 AI 只见 `result_id/item_name/abnormal`，**见不到 exam_no**，按体检号过滤的 SQL 写不出来。

现有 demo 库里就有同样套路：`demo_his` 的 `medical_order`、`fee_detail` 两张表都绑了 `inhos_no → INP_VISIT.visit_no`，`demo_lis.lab_apply` 还把 `patient_no`（LIS 的叫法）也绑到同一个属性——三张表三个列名，指向同一个标准属性，这就是「术语归一」。

**场景四：列名和属性完全对不上——靠列注释救场**

假设新库的表这么建（没有注释）：

```sql
CREATE TABLE tj_dzd (
  tjh   VARCHAR(32),   -- 体检号
  xm    VARCHAR(64),   -- 姓名
  zt    CHAR(1)        -- 状态
);
```

AI 对 `tjh`、`xm` 这种拼音缩写基本无能为力（置信度很低或直接空）。两个补救办法：

1. **推荐做法**：先给表补注释再重新扫描——`ALTER TABLE tj_dzd MODIFY COLUMN tjh VARCHAR(32) COMMENT '体检号';` 然后重新点扫描（幂等，先删后建），AI 靠注释就能配上；
2. 手动在映射页逐行指定 `tjh → PEIS_EXAM.exam_no`、`xm → PEIS_EXAM.person_name`。

这也解释了为什么 demo 库映射质量高：种子数据里每列都有中文注释。**列注释是 AI 映射的第一信号源。**

**场景五：本体里根本没有对应概念——不要硬配**

`peis_exam.remark`（备注）在本体里没有对应属性，AI 返回 `attrCode: ""`。此时：

- **别**把它乱绑到某个相近属性上（错误映射比没有映射更糟，见 4.4）；
- 直接不配。后端会自动把这列记入**概念缺口**（来源 MAPPING_AI，按列注释采集）——「备注」这个词出现在 `/evolve` 缺口页，热度随出现次数增长，后续走 §5 的流程补建概念再回来绑。

#### 4.4 常见的错误映射及后果对照

| 错误           | 例子                                                                    | 用户看到的故障                                       |
| -------------- | ----------------------------------------------------------------------- | ---------------------------------------------------- |
| 绑错概念       | 把`peis_item_result.item_name` 绑到医嘱的 `MEDICAL_ORDER.item_name` | 问数结果张冠李戴：问体检项目，查出来的是医嘱项目     |
| 值字典配反     | `{"1":"在检","0":"完成"}`                                             | 「已完成」查出来的全是在检的，数字对不上业务感觉     |
| 名称列漏绑     | 只绑了`person_name` 所在的主表，忘记 `id_card`                      | 「按身份证号查」这类问题答不了                       |
| 忘点确认       | 映射填了但`confirmed=0`                                               | 表不在白名单，AI 报「表不在白名单」或干脆答不了      |
| 编码列当名称列 | 把`item_code` 绑成 `item_name`                                      | AI 拿中文去做`item_code LIKE '%血常规%'`，永远查空 |

排查口诀：**答不了查确认（confirmed），答错查映射（绑没绑对），翻译错查字典（valueMap）。**

#### 4.5 保存方式与幂等

- 批量保存（`POST /api/mapping/batch`）按「数据源+表+列」判重：**同一列重复保存是覆盖不是新增**，所以改错了直接改回来重存即可；
- 映射可以随时增删（`DELETE /api/mapping/{id}`），不影响本体；但**删除映射会让该列立即退出白名单**，依赖它的问答能力随之失效；
- 建议节奏：**主表全绑 → 验证问数 → 再补从表和枚举列**，每轮验证走一遍 §3 步骤⑥。

#### 4.6 映射做完，顺手补概念关系

本体页给两个新概念连一条边：`PEIS_EXAM --生成结果--> PEIS_ITEM_RESULT`。
概念关系不进白名单（不影响 SQL 能查什么表），但它出现在问数的语义上下文里，帮 AI 理解「一次体检有多条项目结果」这种结构，也让链路追溯 / 影响分析能顺着这条边走。

### 步骤 ⑤：发布本体版本

本体页 → 发布。发布会：

1. 跑**本体自检**：逻辑矛盾（BLOCKER，如继承成环、互斥两端同概念）直接拒绝发布；仅 WARN 需勾选 force；
2. 把所有 PUBLISHED 概念/属性/关系/术语/指标打成**不可变快照**（版本号自动 v(n) → v(n+1)）；
3. 物化传递关系闭包（如「属于」链），查询期零推理成本。

> LLM 问数绑定最新发布版本号，所以**改了本体不发版，AI 还是按旧语义答**。

### 步骤 ⑥：验证

| 验证项       | 操作                     | 预期                                                                                               |
| ------------ | ------------------------ | -------------------------------------------------------------------------------------------------- |
| 映射覆盖度   | 架构全貌页统计卡         | 覆盖度上升                                                                                         |
| 明细问数     | 问「张三的体检做完了吗」 | 生成`SELECT ... FROM peis_exam WHERE person_name LIKE '%张三%'`，证据栏展示 SQL + 数据源 DS_PEIS |
| 枚举反解     | 问「在检的体检有多少」   | WHERE 条件出现`exam_status='0'`（值字典生效的标志）                                              |
| 统计问数     | 问「上个月异常人次」     | `COUNT` + `abnormal='1'` + 按日期过滤                                                          |
| 指标（可选） | 见 §6 绑探针            | 口径卡显示实测值                                                                                   |

问不到时优先排查三件事：**映射 confirmed 了吗 / 概念发布了吗 / 值字典配了吗**。

## 4. 换「已有同类业务」的库（最顺滑场景）

如果新库业务语义与现有本体**同构**（比如另一家医院的 HIS），步骤 ④ 只是「换列名对号入座」：

| 物理列（新库 demo_his2） | 映射到既有概念属性                            | 值字典                        |
| ------------------------ | --------------------------------------------- | ----------------------------- |
| `zyh`                  | `INP_VISIT.visit_no`                        | —                            |
| `bah`                  | `PATIENT.name`（举例：新库把姓名存 bah 列） | —                            |
| `zf_flag`              | `FEE_DETAIL.status`                         | `{"0":"正常","9":"已退费"}` |

本体概念、关系、指标口径**全部复用**，只有映射层换血——这正是「物理自治、逻辑统一」的落地形态：同一个「出院人数」口径，指向不同医院的物理库，数字各自实时可查。

## 5. 概念不够怎么办：两条路

**路 A（正式）**：本体页补建概念 → `DRAFT` → `REVIEW` → `PUBLISHED`（状态机强制，DRAFT 不能直接发布）→ 随下次版本发布。

**路 B（生长回路，推荐先用）**：什么都不建，直接去问数页提问。AI 答不了的词（如「体检套餐」）自动落入**概念缺口**（`/evolve` 页），热度随提问次数增长；积累多了在缺口页 AI 归类 → 一键采纳为术语/草稿概念 → 补属性和映射 → 发布。

> 平台被问得越多，本体长得越全——先用起来，再治理。

## 6. 给新库配指标巡检（可选）

指标页新建指标，绑定**数据源 + 探针 SQL**（探针只写 SELECT，返回单个整数）：

| 字段     | 示例                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 指标编码 | `PEIS_ABNORMAL_CNT`                                                                      |
| 名称     | 体检异常人次                                                                               |
| 口径定义 | 统计周期内 result 表 abnormal=1 的记录数                                                   |
| dsCode   | `DS_PEIS`                                                                                |
| probeSql | `SELECT COUNT(*) FROM peis_item_result WHERE abnormal='1' AND result_id IN (SELECT ...)` |
| 告警阈值 | 如 500                                                                                     |

保存后可手动「实测」，也可配 cron 定时巡检；实测值落库、超阈值进平台内告警中心。问数时指标名直命中还会返回**口径卡**（口径 / 公式 / 探针 SQL / 实测值同源展示）。

## 7. 常见问题（FAQ）

**Q1：接了 Oracle / PostgreSQL 行吗？**
不行。连接层写死 MySQL 驱动与 URL 格式。需要先改造 `DatasourceService` 按 `db_type` 分支（表结构扫描的 `information_schema` 也要换成对应系统目录）。

**Q2：AI 把中文条件写到了编码列上？**
映射时把名称列（如 `person_name`、`item_name`）与编码列（`item_code`）都正确绑定，名称类条件提示词会引导 LLM 用名称列做 LIKE。漏绑名称列是主因。

**Q3：为什么生成的 SQL 报「表不在白名单」？**
该表没有任何 `confirmed=1` 的映射行。回到映射页确认。

**Q4：改了映射 / 本体，问答结果没变？**
本体变更需**发布新版本**才对 LLM 生效（快照机制）。另外问数提示词里有一句演示用提示「业务数据多在 2026-08 月」（`SemanticQaService.buildPlanPrompt`），接真实库后建议顺手改掉，避免相对时间换算被误导。

**Q5：两个库能 JOIN 吗？**
不能。单条 SQL 限定单数据源；跨库核对（如缴费 vs 发药）由应用层分别查询再比对。

**Q6：想撤掉一个库？**
删除映射行与数据源记录即可；本体概念不受影响（但若概念仅服务该库，可走 DEPRECATED 生命周期下线）。删除概念本身受引用保护：有属性/关系/术语/映射/继承边任何引用都会被拒绝并列出数量。
