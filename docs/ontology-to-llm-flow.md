# 本体知识喂给大模型的实现梳理

> 范围：以后端新增与扩展均落在 `bemodel-server-py/` 为准；`bemodel-server/` Java 版只作为历史实现和迁移对照，不再扩展。

## 1. 总体结论

项目并不是把完整 OWL/RDF 图谱一次性塞进大模型，也不是纯向量 RAG。当前实现采用的是“结构化本体元数据 + 场景化提示词 + 程序校验执行”的语义层模式：

1. 本体、术语、指标、物理表扫描结果、字段映射、概念关系都存放在平台库表中。
2. 用户问题进入客服/问数入口后，先由规则或 LLM 做意图路由。
3. 如果是开放业务查询，系统临时拼装一段“本体上下文”，包含概念、属性、物理映射、枚举码值和概念关系。
4. 大模型只负责把自然语言问题编译成受约束的查询计划，或基于本体结构给出业务规则判断。
5. 后端用白名单校验模型返回的 SQL，只允许访问已确认映射的表和列，再去业务库执行。
6. 最终回答再次交给大模型润色时，也只给它“用户问题 + 查询语义 + SQL + 查询结果 JSON”，避免模型凭空编造。
7. 未命中的说法会进入本体缺口表，形成后续补充本体、术语或属性映射的增长回路。

这套设计的关键点是：大模型消费的是被后端“裁剪和格式化后的本体视图”，不是直接获得数据库任意访问权。

## 2. 本体知识来源

### 2.1 标准本体元数据

对应实体在 `bemodel-server-py/src/bemodel/ontology/entities.py`：

- `bm_concept` / `Concept`：概念编码、名称、领域、定义、状态、版本、IRI。
- `bm_attribute` / `Attribute`：概念属性、属性名、数据类型、是否主键、定义。
- `bm_relation` / `Relation`：概念间关系，如 `from_concept -> relation_name -> to_concept`，并保留对称、传递、函数性、逆关系等语义标记。
- `bm_term` / `Term`：业务术语、同义词、来源系统、标准概念。
- `bm_metric` / `Metric`：指标口径、公式、所属概念、探针 SQL、负责人、阈值、最近检测值。
- `bm_ontology_miss` / `OntologyMiss`：未命中的概念、属性或问题，用于本体增长回流。

### 2.2 物理数据源与语义映射

对应实体在 `bemodel-server-py/src/bemodel/datasource/entities.py`：

- `bm_datasource` / `Datasource`：业务数据源连接信息，密码加密保存。
- `bm_physical_table` / `PhysicalTable`：扫描得到的业务表。
- `bm_physical_column` / `PhysicalColumn`：扫描得到的业务字段、类型、注释、主键标记。
- `bm_mapping` / `Mapping`：物理字段到本体属性的映射，核心字段是：
  - `ds_code`
  - `table_name`
  - `column_name`
  - `concept_code`
  - `attr_code`
  - `value_map`
  - `confirmed`

其中 `confirmed = 1` 的映射才会进入语义查询上下文和 SQL 白名单。

## 3. 入口流程：用户问题如何进入语义层

主要入口是 `bemodel-server-py/src/bemodel/cs/router.py`：

- `POST /api/cs/ask`
- 请求体中读取 `question` 和可选的 `scene`
- 调用 `CsService.ask(question, scene)`

`CsService.ask()` 位于 `bemodel-server-py/src/bemodel/cs/services.py`，整体流程是：

1. 判断是否是分析问数场景：`scene == "ANALYTICS"`。
2. 如配置了 `DEEPSEEK_API_KEY`，调用 `DeepSeekClient.chat("CS_ROUTE", ...)` 做意图分类。
3. 如果没有 API Key 或模型未返回有效标签，则走 `route_by_keyword()` 规则兜底。
4. 路由到 `SEMANTIC_QUERY` 时，进入 `SemanticQaService.answer()`。
5. 路由到 `GLOSSARY` 时，进入 `SearchService.search()` 做术语/概念/指标口径查询。

也就是说，本体知识喂给大模型有两条主链路：

- 开放问数/规则问答：`CsService -> SemanticQaService`
- 口径定义问答：`CsService -> SearchService`

## 4. 主链路一：开放语义查询

核心实现：`bemodel-server-py/src/bemodel/cs/semantic.py`

### 4.1 构建本体上下文

方法：`SemanticQaService.build_semantic_context()`

该方法从数据库读取：

- 所有 `status == "PUBLISHED"` 的概念。
- 所有属性。
- 所有物理表注释。
- 所有 `confirmed == 1` 的字段映射。
- 所有概念关系。

然后拼成三段提示词上下文：

1. **本体概念**

   每个概念输出为：

   ```text
   概念编码(概念名称): 属性名/数据类型, 属性名/数据类型
   ```

2. **物理映射**

   按数据源和表分组输出：

   ```text
   DS_HIS:
     medical_order(医嘱表): order_id=MEDICAL_ORDER.医嘱号, status=MEDICAL_ORDER.状态{0=开立,1=执行,2=取消}
   ```

   这里模型看到的不是裸表结构，而是“物理列 = 本体概念.标准属性”。如果 `value_map` 存在，还会把枚举码值一并给模型，用于把中文状态反解成原始码。

3. **概念关系**

   输出为：

   ```text
   FROM_CONCEPT(中文名) --关系名--> TO_CONCEPT(中文名)
   ```

这一步就是“本体知识喂给大模型”的核心：把平台的结构化语义层压缩成可读的 prompt context。

### 4.2 让模型生成查询计划

方法：`SemanticQaService.plan_query(q)`

它将：

```text
build_semantic_context()
+ SEMANTIC_PLAN_PROMPT
+ 用户问题
```

一起传给：

```python
DeepSeekClient.chat(
    "CS_SEMANTIC_PLAN",
    "你是医疗信息平台的本体语义查询规划器，把自然语言问题编译为只读 SQL。只返回JSON，不要多余文字。",
    prompt,
)
```

模型必须返回 JSON，支持三种模式：

- `QUERY`：可以通过业务库查询回答。
- `MODEL_ANSWER`：业务规则类问题，不一定查数据，基于本体结构判断，可附带验证探针 SQL。
- `UNANSWERABLE`：当前语义层回答不了。

`QUERY` 的典型结构是：

```json
{
  "mode": "QUERY",
  "ds": "DS_HIS",
  "sql": "SELECT ... LIMIT 100",
  "semantics": "一句话说明查了什么、用了哪些概念"
}
```

`MODEL_ANSWER` 的典型结构是：

```json
{
  "mode": "MODEL_ANSWER",
  "ds": "DS_CHARGE",
  "semantics": "基于哪个概念/关系/属性的结构判断",
  "conclusion": "可以/不可以 + 依据",
  "verifySql": "可选的 SELECT 探针 SQL"
}
```

### 4.3 SQL 安全校验

模型返回 SQL 后，不会直接执行。`SemanticQaService.answer()` 会先调用：

```python
validate_sql(plan["sql"], tables, columns)
```

校验逻辑在 `bemodel-server-py/src/bemodel/cs/sql_validation.py`：

- SQL 必须是单条 `SELECT`。
- 禁止 `INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE/...` 等关键字。
- 禁止分号多语句。
- `FROM/JOIN` 里的表必须在当前数据源已确认映射表白名单中。
- 所有列名必须在已确认映射列白名单中。
- 未带 `LIMIT` 自动补 `LIMIT 100`。
- 超过 `LIMIT 100` 会被改写为 `LIMIT 100`。

白名单来源是：

```python
Mapping.ds_code == plan["ds"]
Mapping.confirmed == 1
```

因此模型即使编出未映射表或未映射列，也会被后端拒绝。

### 4.4 执行业务库查询

方法：`SemanticQaService.execute(ds, sql)`

执行时通过 `DatasourceService.jdbc(ds)` 获取动态业务库连接：

- 设置 MySQL 会话超时：`max_execution_time=15000`
- 执行只读 SQL
- 最多取前 100 行
- 给最终回答只展示前 20 行

### 4.5 让模型基于结果生成自然语言回答

查询完成后，后端再次调用大模型：

```python
DeepSeekClient.chat("CS_SEMANTIC_ANSWER", system_prompt, user_prompt)
```

这次喂给模型的不是完整本体，而是受控结果：

- 用户问题
- 查询语义 `plan["semantics"]`
- 实际执行 SQL
- 结果行数
- 结果 JSON，最长截断到约 3000 字符

系统提示明确要求：

- 严格基于给定查询结果回答。
- 先给结论再给关键数字。
- 结果里没有的信息不要编造。
- 结果为 0 条就如实说明。

如果模型不可用，则程序用固定模板兜底，例如“按本体映射查询到 N 条记录”。

### 4.6 业务规则类问题

当 `plan["mode"] == "MODEL_ANSWER"` 时，进入 `SemanticQaService.model_answer()`：

1. 先读取模型返回的本体结构判断和初步结论。
2. 如果带有 `verifySql`，仍然走同一套 SQL 白名单校验和执行。
3. 再把“用户问题 + 本体结构判断 + 初步结论 + 验证探针结果”喂给 `CS_SEMANTIC_ANSWER`。
4. 如果模型不可用，返回结构化兜底结论。

这类问题的特点是：模型的依据来自“概念、属性、关系”的结构，而不是直接让模型凭常识回答。

## 5. 主链路二：口径、术语、指标问答

核心实现：`bemodel-server-py/src/bemodel/search/services.py`

入口包括：

- `GET /api/search?q=...`
- `CsService.glossary_answer()`

`SearchService.search(query)` 的流程：

1. 遍历 `Term`，匹配业务术语名称。
2. 遍历 `Concept`，匹配概念名称或定义片段。
3. 遍历 `Metric`，匹配指标名称或定义片段。
4. 命中后拼装命中列表，包括类型、标题、概念编码、指标编码、定义、公式等。
5. 将命中结果拼入 prompt，调用：

```python
DeepSeekClient.chat(
    "SEARCH_ANSWER",
    "你是医疗本体平台的口径解答助手，严格基于给定定义回答。",
    prompt,
)
```

这里模型吃到的不是全量本体，而是检索命中的术语、概念或指标定义。它的职责是把平台已有定义组织成用户能读懂的答案。

如果没有命中并且允许记录缺口，则调用：

```python
MissService.record_miss(query, "CONCEPT", "SEARCH")
```

## 6. 辅助链路：AI 辅助字段映射

核心实现：`bemodel-server-py/src/bemodel/datasource/services.py` 的 `MappingService.ai_suggest()`

这条链路不是用户问答，但同样体现了“本体知识喂给模型”：

1. 读取某个物理表的字段名、数据类型、字段注释。
2. 读取已发布概念和全部属性。
3. 拼装 prompt：
   - 物理表字段列表
   - 可选标准概念及属性列表
4. 调用：

```python
DeepSeekClient.chat(
    "MAPPING_SUGGEST",
    "你是医疗信息化本体映射专家。只返回JSON数组，不要多余文字。",
    prompt,
)
```

模型返回字段到 `conceptCode/attrCode` 的推荐映射。后端会校验返回字段必须确实存在于该物理表；模型不可用时降级为列名/注释与属性名的规则匹配。

这一步相当于让模型帮助维护“物理数据 -> 本体属性”的桥，后续语义查询正是依赖这些 `confirmed` 映射。

## 7. LLM 统一封装与审计

核心实现：`bemodel-server-py/src/bemodel/llm/services.py`

`DeepSeekClient.chat(call_type, system_prompt, user_prompt)` 做了几件事：

1. 如果 `DEEPSEEK_API_KEY` 未配置，直接记录失败日志并返回 `None`。
2. 调用 DeepSeek 兼容的 `/chat/completions` 接口。
3. 固定 `temperature = 0.2`，降低发散。
4. 从响应中取 `choices[0].message.content`。
5. 无论成功失败，都写入 `bm_llm_log`。

审计表实体在 `bemodel-server-py/src/bemodel/llm/entities.py`：

- `call_type`：调用场景，如 `CS_ROUTE`、`CS_SEMANTIC_PLAN`、`CS_SEMANTIC_ANSWER`、`SEARCH_ANSWER`、`MAPPING_SUGGEST`。
- `model`：模型名。
- `ontology_version`：当前发布版本标签，来自 `ReleaseService.current_tag()`。
- `prompt_digest`：提示词摘要，最多 200 字符。
- `latency_ms`
- `success`
- `err_msg`
- `created_at`

这让每次“本体喂给模型”的调用都能按本体版本追溯。

## 8. 缺口回流：模型答不了时如何反哺本体

项目没有把未命中问题简单丢弃，而是记录为本体增长素材：

- `SearchService.search()` 未命中口径时，记录 `kind = "CONCEPT"`、`source = "SEARCH"`。
- `SemanticQaService.answer()` 规划为 `UNANSWERABLE` 或 SQL 执行失败且语义层无法回答时，记录 `kind = "QUESTION"`，来源为 `QA_ASK` 或 `CS_ASK`。
- `MappingService.ai_suggest()` 对无法匹配的字段记录 `kind = "ATTRIBUTE"`、`source = "MAPPING_AI"`。

这些数据落入 `bm_ontology_miss`，前端可在本体扩展提案里处理，后续可采纳为术语、概念或属性映射。

图中最关键的是 `本体上下文组装 → LLM 生成查询计划` 这一段：代码把概念、属性、映射、关系整理成提示词上下文，随当前问题一起发给大模型。这里是“喂知识”，不是训练模型，也不会更新模型权重。

| 图中节点 | 对应代码 | 作用 |
| --- | --- | --- |
| 问题路由判断 | `cs/services.py → CsService.ask()` | 判断是问数、问口径，还是专用业务问题 |
| 本体上下文组装 | `cs/semantic.py → build_semantic_context()` | 拼出本体概念、物理映射、概念关系三段文字 |
| LLM 生成查询计划 | `cs/semantic.py → plan_query()` | 调用 `CS_SEMANTIC_PLAN`，让模型返回结构化计划 |
| SQL 安全校验 | `allowed()`、`sql_validation.py → validate_sql()` | 用表/列白名单和 SELECT 规则拦截风险 SQL |
| 查询业务库 | `cs/semantic.py → execute()` | 连接数据源，设置超时，最多取回 100 行 |
| LLM 组织答案 | `answer() → DeepSeekClient.chat()` | 把问题、SQL、结果交给模型组织中文答案 |

表中的文件路径均相对于 `bemodel-server-py/src/bemodel/`。

### 9.2 本体上下文生成：平台知识如何变成提示词？

```text
                         ┌──────────────────┐
```

## 10. 一次完整调用示例

以“内科昨天缴费总额是多少？”这类问数为例：

1. 前端调用 `POST /api/cs/ask`，body 中带 `question`。
2. `CsService.ask()` 调用模型或规则判断为 `SEMANTIC_QUERY`。
3. `SemanticQaService.build_semantic_context()` 读取发布概念、属性、确认映射和概念关系，拼成上下文。
4. `SemanticQaService.plan_query()` 请求模型生成 JSON 查询计划。
5. 模型根据上下文选择某个数据源，例如 `DS_CHARGE`，并生成只读 SQL。
6. 后端从 `bm_mapping` 取该数据源允许访问的表和列。
7. `validate_sql()` 校验 SQL 只读、单语句、表列均在白名单内，并限制 `LIMIT 100`。
8. `execute()` 连接实际业务库执行 SQL。
9. 后端把结果行数、结果 JSON、SQL、查询语义交给模型生成最终中文回答。
10. 返回结果包含 `answer`、`evidence`、`semantics`、`rows`、相关本体页链接。

## 11. 关键设计取舍

### 11.1 模型负责语义翻译，不负责权限边界

模型可以提出 SQL，但 SQL 能不能执行由后端决定。权限边界来自 `bm_mapping.confirmed == 1`、SQL 白名单、只读关键字校验和行数限制。

### 11.2 本体作为“可执行语义层”

本体不只是概念展示页。它通过 `Mapping` 把概念属性绑定到真实业务库字段，通过 `Relation` 表达业务关系，通过 `Metric` 表达指标口径。模型消费的是这层结构，从而能把自然语言落到真实表列。

### 11.3 不是黑盒问答，而是可追溯问答

返回结果会带：

- 执行 SQL
- 数据源
- 结果行数
- 查询语义
- 相关概念链接

同时 `bm_llm_log` 记录调用类型、模型、本体版本、提示词摘要和耗时。

### 11.4 有模型降级路径

如果没有 API Key 或模型调用失败：

- 路由可退回关键词规则。
- 查询回答可用模板兜底。
- 字段映射可退回列名/注释规则匹配。
- 答不了的问题进入本体缺口回流。
